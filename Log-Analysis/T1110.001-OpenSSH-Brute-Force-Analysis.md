## Executive Summary

Analysis of the OpenSSH authentication logs identified a sustained and globally distributed brute-force and credential-stuffing campaign targeting the Linux host **LabSZ**. Between **06:55:46** and **09:13:42** on **December 10**, numerous external IP addresses attempted to authenticate using common administrative, default, and application-specific usernames including `root`, `admin`, `support`, `webmaster`, `pgadmin`, `ubnt`, `cisco`, and `pi`.

The attack exhibited characteristics consistent with automated botnet activity, including high-velocity password guessing, dictionary attacks, credential spraying, repeated pre-authentication disconnects, and Java-based automation using the JSch framework. During peak attack windows, the OpenSSH daemon spawned dozens of authentication processes within minutes, increasing authentication workload and system overhead.

No successful logins were observed within the analyzed timeframe. All authentication attempts resulted in failures, protocol errors, or client disconnects, indicating that the attack was unsuccessful but persistent. The findings highlight the need for stronger SSH hardening, network access restrictions, automated blocking mechanisms, and continuous monitoring to reduce exposure to internet-wide credential attacks.

# Threat & Anomaly Analysis

## [High] Automated Botnet / Password Spraying Signatures
The distribution of IPs across vast geo-locations (ranging from AWS CN pools, Mexican UniNet infrastructure, European PoneyTelecom, to global consumer DSL links) combined with near-identical target wordlists confirms an orchestrated, internet-wide automated botnet credential-stuffing/brute-force event.

## [High] Tooling Fingerprinting
### JSch Framework:
Host `195.`154.`37.`122` exposed its technical identity via explicit error logs generated during its session collapse:
> com.jcraft.jsch.JSchException : Auth fail.
This proves a Java-based automated exploit payload or script was running actively against the server.

### Pre-Auth Disconnects:
Multiple entries indicate connections closing immediately without sending identification strings or completing authentication phases—pointing directly to automated port scanning utilities (e.g., Nmap version detection or masscan scripts checking port state).

## [Medium] Reverse Mapping Failures
The system flags _POSSIBLE BREAK-IN ATTEMPT!_ for IPs like `173.`234.`31.`186` and `191.`210.`223.`172`. This alert indicates a DNS pointer mismatch (Forward DNS lookup does not map back cleanly to the source IP triggering the connection). While common on public dynamic IP address spaces, it explicitly confirms external, unauthenticated nodes hitting the perimeter gateway.

# 5. Operational & Performance Analysis

**Process Exhaustion:** During peak windows (specifically around 09:11:20 to 09:13:42), the OpenSSH daemon was forced to spawn up to 25 separate processes in less than 2 minutes to evaluate inbound connection requests. This behavior forces an increase in system interrupts and context switching.

**PAM Overhead:** Multiple warning messages indicating PAM service(`sshd`) ignoring max retries reveal that the SSH processing framework was contextually overloaded by bad actors pushing multiple parameters inside monolithic TCP flows. If sustained, this would induce localized exhaustion of available kernel PIDs or pluggable authentication module resources.

# 6. Root Cause Analysis

## Confirmed Facts
- The server **LabSZ** has its SSH port (`TCP/22`) directly exposed to the open internet.
- A minimum of **14 unique global IP addresses** engaged the system over a ~2.5-hour span.
- **0% authentication success rate** is present in the provided forensic timeline.
- Attackers focused on broad horizontal scanning (**admin, root, cisco, ubnt, pgadmin**) rather than specific targeted compromises against custom enterprise users.

## Inferred Hypotheses
- **Hypothesis 1 (Confidence: Critical):** The target system is unshielded by network-level access control lists (ACLs), host-based connection limiters (such as Fail2ban), or geo-blocking profiles.
- **Hypothesis 2 (Confidence: High):** The infrastructure has been picked up by active global scanning nodes and indexed on malicious botnet operational lists as an available target for standard password spraying.

# 7. Recommendations

## Immediate Containment Steps
- **Host-Based Access Limitation:** Instantly deploy fail2ban or sshguard to dynamically drop traffic at the firewall (`iptables`/`nftables`) level for any endpoint generating more than 3 failed auth attempts within a 15-minute window.
- **Network Perimeter Security:** Whitelist trusted source IP ranges for access to administrative assets. Completely disable universal inbound routing to port `22` from the public internet (`0.0.0.0/0`).

## Hardening & Configuration Best Practices
- **Enforce Public-Key Authentication:** Adjust `/etc/ssh/sshd_config` to explicitly enforce cryptographic keys and disable standard password challenges:
```plaintext
PasswordAuthentication no
PubkeyAuthentication yes
ChallengeResponseAuthentication no
```
- **Disable Root Logins:** Prevent direct targeting of administrative structures by configuring:
```plaintext
PermitRootLogin no
```
- **Alternative Port Routing:** Shift the default binding port of the SSH daemon away from standard TCP/22 to a non-standard ephemeral port (e.g., TCP/2222 or higher). This stops more than 95% of automated script scans from polluting system logs.

## Monitoring Improvements
- **SIEM / Logging Alerts:** Construct a centralized ingestion pipeline rule tracking `sshd` process creation. Generate high-severity alerts when unique source IPs register patterns mirroring PAM service(`sshd`) ignoring max retries.
- **Log Correlation Request:** To rule out a complex low-and-slow breach, request further endpoint protection logs (`auditd`), active bash command history histories, and outbound firewall tracking maps to confirm no secondary network anomalies occurred during or after this period.
